\section{Objetivo del Capítulo}

Este capítulo documenta el módulo de postprocesamiento espectral desarrollado para analizar, en un entorno centralizado en la nube, las capturas generadas por el sistema de monitoreo SDR. El objetivo es explicar cómo el software recibe una traza espectral, organiza la información de frecuencia y amplitud, detecta emisiones candidatas y extrae sus parámetros técnicos: frecuencia central ($F_c$), ancho de banda (BW / OBW), potencia ($power\_dbm$), y opcionalmente indicadores de calidad (MER/BER estimado para TDT).

Adicionalmente, el módulo verifica el cumplimiento de emisiones detectadas contra una base de licencias y las asocia administrativamente a un municipio o código DANE.

\section{Alcance y Exclusiones}

\subsection{Lo que implementa este módulo}

\begin{itemize}
\item Localización administrativa: asociación de una emisión al municipio o código DANE del sensor que capturó la señal.
\item Análisis espectral: detección, medición de $F_c$, BW, OBW, potencia, SNR.
\item Comparación contra base de licencias CSV.
\item Exportación de resultados en JSON.
\item Operación vía CLI (\texttt{main.py}) y API REST (\texttt{server\_flask.py}).
\end{itemize}

\subsection{Lo que NO implementa este módulo}

\begin{itemize}
\item Localización radioeléctrica real: no se realiza triangulación, TDOA, AOA ni multilateración RSSI. La posición física del transmisor NO se estima.
\item Localización geográfica del sensor: no se usa GPS/geotag para estimar posición del emisor.
\item Demodulación formal de señal: MER/BER se estiman desde traza espectral, no desde demodulación.
\item Evaluación de vigencia de licencias: el código no filtra licencias vencidas en esta versión.
\end{itemize}

\textbf{NOTA TÉCNICA:} La distinción entre localización administrativa, localización del sensor y localización radioeléctrica real es fundamental para evitar conclusiones regulatorias incorrectas. Asociar una emisión a un municipio no prueba que el transmisor esté físicamente allí.

\section{RBW, FFT y Resolución Espectral}

\subsection{Relación entre parámetros}

La resolución espectral del sistema está determinada por la cadena de adquisición SDR. Los parámetros clave son:

\begin{itemize}
\item Sample rate (\texttt{sample\_rate\_hz}): por defecto 20 MHz (20\,000\,000 Hz); configurable por campaña.
\item RBW (\texttt{rbw\_hz}): se define en el backend como \texttt{campaign.resolution\_khz * 1000} si está configurado; si no, valor por defecto de 10\,000 Hz (10 kHz).
\item FFT size: no se selecciona explícitamente en postprocesamiento. El módulo recibe \texttt{Pxx} ya calculado por el sensor. El número de bins es \texttt{len(Pxx)} y la resolución de bin se calcula como: \texttt{bin\_hz = (end\_freq\_hz - start\_freq\_hz) / (N - 1)}.
\item La fórmula teórica RBW = Sample Rate / FFT\_size aplica en el sensor; en postprocesamiento se usa la resolución implícita del vector \texttt{Pxx} recibido.
\end{itemize}

\subsection{Distinción entre resolución de visualización y exactitud de medición}

La resolución espectral determina la separación mínima entre frecuencias distinguibles, pero no es equivalente a la exactitud de medición. Un bin de 10 kHz RBW no implica que la frecuencia central se mida con error de 10 kHz; el centroide de potencia puede dar mayor precisión. Sin embargo:

\begin{itemize}
\item El hardware SDR con ancho instantáneo de 20 MHz limita el span analizable sin barrido.
\item La exactitud de amplitud está limitada por la planicidad del receptor y se corrige con el archivo de corrección (ver Sección 7).
\item A mayor RBW, menor tiempo de adquisición pero peor resolución para señales angostas.
\end{itemize}

\section{Calibración y Corrección de Ganancia}

\subsection{Qué corrige el archivo de corrección}

El archivo CSV de corrección (parámetro \texttt{--corr}) contiene dos columnas: Frecuencia (MHz) y Error (dB). Se aplica como:

\begin{displaymath}
\text{amplitudes\_dbm\_corregidas} = \text{amplitudes\_dbm} + \text{correction\_dB}(f)
\end{displaymath}

Esto corrige la respuesta en frecuencia del sistema. Puede absorber: desbalance de respuesta del receptor SDR, no planicidad (ripple) espectral, pérdidas en cable/antena y offsets de ganancia dependientes de frecuencia.

\subsection{Cómo se genera y periodicidad}

\begin{itemize}
\item El archivo de corrección debe generarse externamente (no hay rutina automática en este repositorio).
\item Se recomienda generarlo con una fuente de referencia calibrada (generador de señal o analizador de espectro certificado).
\item Periodicidad recomendada: calibración semestral o ante cambio de hardware/antena.
\item Si no se suministra archivo de corrección, \texttt{Pxx} se usa sin ajuste. Esto puede afectar la exactitud de potencia, umbral de detección y ancho de banda en receptores con respuesta no plana.
\end{itemize}

\section{Análisis Espectral}

\subsection{Frecuencia Central}

La frecuencia central se calcula como el centroide de potencia (baricentro energético) dentro de los límites de la emisión detectada, no como el punto de máxima amplitud. Esto garantiza mayor precisión en señales asimétricas (ej. FM con piloto estéreo).

\begin{tabular}{p{4cm}p{3cm}p{7cm}}
\textbf{Campo} & \textbf{Unidad} & \textbf{Descripción} \\
\hline
\texttt{fc\_hz} & Hz & Frecuencia central estimada en unidad base \\
\texttt{fc\_mhz} & MHz & \texttt{fc\_hz} escalado; para reportes \\
\texttt{matched\_peak\_hz} & Hz & Pico más cercano a la frecuencia solicitada (modo peaks) \\
\texttt{delta\_match\_hz} & Hz & Diferencia entre frecuencia solicitada y pico asociado \\
\end{tabular}

\subsection{Ancho de Banda}

Se calculan en paralelo dos métricas: OBW (Occupied Bandwidth, 99\% de la potencia) y ancho a \,-x dB respecto al pico. El sistema prefiere reportar OBW por ser más estable en señales OFDM, FM estéreo y señales con múltiples picos. Solo si OBW no es válido se usa el criterio \,-x dB.

\begin{tabular}{p{4cm}p{3cm}p{7cm}}
\textbf{Campo} & \textbf{Unidad} & \textbf{Descripción} \\
\hline
\texttt{bandwidth\_xdb\_hz} & Hz & Ancho a \,-x dB respecto al pico \\
\texttt{obw\_hz} & Hz & OBW: intervalo con 99\% de la potencia \\
\texttt{bw\_hz} & Hz & Ancho de banda seleccionado para reporte (OBW preferido) \\
\texttt{bw\_khz} & kHz & \texttt{bw\_hz} en kHz \\
\texttt{bw\_medido\_kHz} & kHz & Nombre en modo compliance \\
\end{tabular}

\subsection{Potencia}

El cálculo de potencia NO suma directamente valores en dBm. El procedimiento correcto es:

\begin{enumerate}
\item Convertir cada muestra \texttt{Pxx[i]} de dBm a dominio lineal: $P_{lin}[i] = 10^{(Pxx[i]/10)}$ [mW].
\item Sumar la contribución de todos los bins en la región de emisión: $P_{total\_mW} = \sum (P_{lin}[i] * \texttt{bin\_hz})$.
\item Convertir de vuelta a dBm: $power\_dbm = 10 \cdot \log_{10}(P_{total\_mW})$.
\item Si la suma produce valor no finito (NaN, $-\infty$), \texttt{power\_dbm} se reporta como \texttt{null}.
\item Fallback: si la suma directa falla, se intenta integración trapezoidal como segundo recurso.
\end{enumerate}

Distinción importante: \texttt{power\_dbm} es potencia integrada de la emisión. \texttt{channel\_power\_dbm} es potencia de canal calculada en la medición de parámetros. Ambas son distintas de la potencia de pico (amplitud máxima del bin).

\subsection{Indicadores Estimados de Calidad (MER/BER)}

\textbf{ADVERTENCIA:} MER y BER estimados desde traza espectral NO equivalen a medición formal con demodulación. Estos valores son indicadores de diagnóstico preliminar únicamente.

\begin{itemize}
\item Solo aplican a señales TDT (rango de frecuencias TDT Colombia y ancho de banda plausible para OFDM).
\item Se estiman usando la relación señal/ruido en banda vs. fuera de banda, asumiendo modulación 64-QAM.
\item Una medición formal de MER/BER requiere demodulación completa de la señal o equipo especializado certificado.
\item Si la SNR es insuficiente para una estimación confiable, los campos \texttt{mer\_db} y \texttt{ber\_est} se omiten del resultado.
\end{itemize}

\begin{tabular}{p{4cm}p{3cm}p{6cm}}
\textbf{Campo} & \textbf{Unidad} & \textbf{Descripción} \\
\hline
\texttt{mer\_db} & dB & Indicador estimado de calidad de modulación (solo TDT, solo diagnóstico) \\
\texttt{ber\_est} & -- & Indicador estimado de tasa de error de bit (solo TDT, solo diagnóstico) \\
\texttt{f\_center\_hz} & Hz & Centro de la banda usada para el cálculo \\
\texttt{band\_start\_hz} & Hz & Límite inferior de la banda evaluada \\

\begin{tabular}{p{4cm}p{6cm}p{4cm}}
\textbf{Criterio} & \textbf{Regla} & \textbf{Comportamiento} \\
\hline

\end{tabular}

\subsection{Manejo de múltiples licencias y licencias sin vigencia}

\begin{itemize}
\item Si varias licencias coinciden en la misma ventana de DANE: el sistema selecciona una sola licencia usando $score = |\Delta f|$ como criterio principal y $|\Delta bw|$ como desempate secundario. Potencia no decide el match.
\item Si hay empate exacto en score: se toma el primer registro que aparece en el CSV (índice más bajo).
\item No se reportan múltiples licencias candidatas en esta versión.
\item Vigencia de licencias: el código actual NO evalúa fechas ni filtra licencias vencidas. Si el CSV contiene columnas de fecha, no se usan. Esta funcionalidad queda pendiente.
\end{itemize}

\section{Localización Administrativa}

\subsection{Qué es la localización administrativa}

La localización administrativa consiste en asociar una emisión detectada al municipio o código DANE del sensor que realizó la captura. Esto permite contextualizar la medición dentro de una zona de análisis y filtrar la base de licencias por área geográfica.

\subsection{Origen del parámetro territorial}

\begin{tabular}{p{4cm}p{6cm}p{4cm}}
\textbf{Interfaz} & \textbf{Mecanismo} & \textbf{Referencia en código} \\
\hline
API HTTP & Campo municipio en body/meta de la petición, o query param & \texttt{server\_flask.py} (líneas 308--336) \\
CLI / consola & Argumento \texttt{--municipio} en terminal & \texttt{main.py} (líneas 150--235) \\
Backend de reportes & Objeto ubicacion con municipio y código DANE inyectado al invocar el servicio & \texttt{reports.ts} (líneas 253--271) \\
\end{tabular}

\subsection{Jerarquía de prioridad}

\begin{itemize}
\item Prioridad 1 — \texttt{danes} (lista): si se entrega lista de códigos DANE, se ignoran los demás campos territoriales.
\item Prioridad 2 — \texttt{dane} (único): si no hay lista, se evalúa un único código DANE.
\item Compatibilidad: si \texttt{municipio} es numérico, se interpreta como código DANE.
\item Protección contra falsos positivos: si no se especifica ningún filtro territorial, el procesador aborta el matching con el CSV de licencias.
\end{itemize}

\subsection{Limitaciones de la localización administrativa}

\textbf{NOTA TÉCNICA: ADVERTENCIA REGULATORIA:} Asociar una emisión a un municipio NO prueba que el transmisor esté físicamente en ese municipio. La medición depende de la ubicación del sensor, la cobertura de la señal, la propagación, la altura y el patrón de antena, y la base de licencias disponible. Emisiones provenientes de municipios cercanos pueden aparecer como detectadas en el municipio del sensor.

\begin{itemize}
\item La cobertura de una señal puede cruzar límites municipales, especialmente en zonas de montaña o con topografía favorable.
\item Para determinar la ubicación física del transmisor se requiere localización radioeléctrica real (TDOA, AOA, multilateración), no implementada en este módulo.
\end{itemize}

\section{Limitaciones del Módulo}

\textbf{[Implementado]} Análisis espectral: $F_c$, BW, OBW, potencia, SNR.

\textbf{[Implementado]} Comparación contra licencias con filtro DANE/municipio.

\textbf{[Parcial]} Trazabilidad: timestamp y sensor\_id implementados; hash de captura pendiente.

\textbf{[Parcial]} Seguridad: JWT en backend; TLS depende de infraestructura externa.

\textbf{[Pendiente]} Evaluación de vigencia de licencias (fechas en CSV no se evalúan).

\textbf{[Pendiente]} Reporte de múltiples licencias candidatas para una misma emisión.

\textbf{[Pendiente]} Hash/firma del payload espectral para integridad de datos.

\textbf{[Recomendado]} Localización radioeléctrica real (TDOA, AOA, multilateración RSSI).

\textbf{[Recomendado]} Rutina automática de generación del archivo de corrección de ganancia.

\textbf{[Recomendado]} Modelos de IA/ML para detección robusta en baja SNR.

\textbf{[Recomendado]} Compresión de trazas y procesamiento por eventos en el borde.

\section{Recomendaciones}

\begin{itemize}
\item Implementar evaluación de vigencia de licencias: agregar columna de fecha al CSV y filtrar registros vencidos antes del matching.
\item Agregar hash SHA-256 del payload JSON de cada captura para trazabilidad forense.
\item Aplicar middleware JWT al router de sensor (\texttt{sensor.ts}) para autenticar nodos remotos.
\item Configurar TLS/HTTPS en producción mediante proxy inverso (nginx, traefik).
\item Antes de migrar a Deep Learning, evaluar mejoras clásicas: CFAR optimizado, mejor estimación de piso de ruido por segmentos, compresión de trazas en el borde.
\item Validar con datasets etiquetados (señales reales con ground truth conocido) antes de reportar métricas de desempeño al ANE.
\item Documentar y estandarizar el proceso de generación del archivo de corrección de ganancia (periodicidad semestral recomendada).
\end{itemize}
